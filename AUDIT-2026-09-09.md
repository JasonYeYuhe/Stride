# Stride audit — 2026-09-09

Multi-agent audit of the shipped codebase, run twice (the first pass lost 62 verifier
agents to a session limit; the second completed). Eight dimensions found **53** candidate
defects; each was then attacked by 2–3 independent agents whose only job was to refute it.

**31 confirmed · 21 refuted · 0 unverified.**

Six items are already fixed and shipped in 1.2.2 — see `RELEASE-1.2.2.md`. The list below
is what remains. One item (the sync body limit) has since been fixed and deployed server-side.

> A note on the refuted 21: they are not noise. Findings like "the ModelContainer
> `fatalError` crashes the widget on launch" and "logout leaks the previous user's sync
> queue" read as plausible and are wrong — the guard exists a few lines up, or the path is
> unreachable. Re-raising them wastes a day each. That is what the verify stage is for.

## Executive summary

First, a correction to the brief: the repo is no longer at 4521638. HEAD is a2dbc9d, tagged v1.2.2, and 1.2.2 already shipped fixes for six of the reported items. I re-opened every file and confirmed these are CLOSED — do not re-fix them: the snake_case push encoding (APIClient.swift now carries a comment explaining why the strategy must not be set), the percent-encoded `?since=` pull URL (now built with URLComponents), SharedModelContainer being a computed var (now `static let`), the non-idempotent `dayKey` that zeroed every streak in the Americas (dayKey now returns an existing day-key unchanged), magic-link tokens in the request log, and — the big one — the widget extension never being embedded in the .app (project.pbxproj now has 3 copy-files phases where it had 0). That was excellent work and it changes the priority order of what is left.

Nineteen defects remain open, and the highest-priority one is a direct consequence of 1.2.2 succeeding. Sync push worked for the first time ever in 1.2.2. `pushLocal` sends a full snapshot of every habit and every check-in on every sync, and `server/index.js:86` caps every JSON body at 10 KB. I measured the real wire shapes (habit 394 B, entry 171 B) and ran the actual express config: 50 entries → 200, 60 entries → 413 "request entity too large". Three habits and roughly 53 check-ins is the ceiling — under two weeks of daily use. Past it, push 413s, `pushLocal` throws before `pullRemote` runs, and sync is dead permanently in both directions with no self-healing, because the payload only grows. Every user who signs in on 1.2.2 is on a two-week fuse. This is server-side, deployable today, no App Review.

After that the open items cluster into four groups. Sync reconciliation still has three real defects in SwiftData-facing code: UUIDs compared as raw case-sensitive strings (which breaks the App Review demo account specifically and can hard-crash at launch), a `Dictionary(uniqueKeysWithValues:)` duplicate-key trap, and deletion tombstones erased from UserDefaults before the network push, so any failed push loses them forever — which is not an edge case while the 10 KB bug is live. The check-in write path is the same bug copied into four places: the widget, watch and Siri intents all treat every habit as binary, so one widget tap on a partially-logged count habit deletes the whole day and pushes a tombstone for it. Payments have two silent failures: a charged-but-unverified purchase is dropped with no Pro, no error and no finished transaction (so it re-drops on every launch, forever), and the entitlement read is the last of four sequential network awaits at launch, so a paying user can see Pro locked for ~40 s on a bad connection. And the stats math has five separate places where a correct user is shown a wrong number, including two paid-tier screens — "Gym, Mon/Wed/Fri, six perfect weeks" renders as "Current Streak 18 days / Best Streak 1 days" on the same row.

I am flagging two items as real but not worth fixing in 1.2.3: the 1.1-client field wipe (verified against git dbdab48, but it needs a dynamic UPDATE SET rewrite of the hottest server path to protect a shrinking pre-June cohort) and making `pushLocal` incremental (correct long-term, but it is the largest change here and the 5 MB limit buys years of headroom). Everything else is worth doing, and most of it batches into five commits.

One process note: the fastest way to catch the demo-account bug before Apple does is to log into demo@stride-review.com on a device and check that habits show streaks and history. That is the acceptance test for the UUID-case fix, and it is the item most likely to get 1.2.3 rejected if skipped.

## Must fix

### Sync push exceeds the server's 10 KB body limit after ~2 weeks — sync dies permanently, in both directions

**Where:** `server/index.js:86 (global express.json limit) + Stride/Sources/Services/SyncService.swift:102-167 (unfiltered full-snapshot push)`  
**Effort:** ~30 min including deploy

pushLocal does an unfiltered `context.fetch(FetchDescriptor<Habit>())` and a `habits.flatMap { habit.records }` — it serialises every habit and every check-in the device has ever recorded, on every single sync. There is no incremental filter and no chunking, so the body grows monotonically while the ceiling stays at 10 KB. I measured the real wire shapes: one habit object is 394 bytes, one entry 171 bytes; 3 habits + 50 entries = 9,884 B (passes), 3 habits + 53 entries crosses. Verified empirically against the identical express config: 50 entries (8,625 B) -> 200; 60 entries (10,345 B) -> 413 {"error":"request entity too large"}. body-parser raises PayloadTooLargeError, the handler at index.js:154-165 preserves the 413, APIClient throws, and pushLocal throws BEFORE pullRemote runs — so the user loses pull as well as push. Nothing is ever backed up again, no tombstone is delivered, remote changes stop arriving, and Settings shows a generic error. It never recovers on its own because the client resends the same, now larger, payload every time. This is the wall every 1.2.2 user hits within a fortnight of signing in.

**Fix:** Give the sync router its own body limit and keep 10 KB everywhere else. Mount the larger parser BEFORE the global one (body-parser sets req._body and the first parser to run wins): insert `app.use("/v1/sync", express.json({ limit: "5mb" }));` immediately above index.js:86, and add the same for the legacy `/sync` alias mounted at :100. I verified this exact arrangement: a 206,425-byte push to /v1/sync/push returns 200 with all 1200 entries parsed, while a 20,012-byte POST to /v1/auth/request-link still returns 413. Also add an explicit per-request cap on habits.length / entries.length in the push handler returning a clear 400, so a runaway client gets a diagnosable error rather than a bare 413. Server-only — deploy today without waiting on App Review.

### Deletion tombstones are erased from UserDefaults before the push succeeds — deleted habits come back and cannot be re-deleted

**Where:** `Stride/Sources/Services/SyncService.swift:103 (consumeDeletedIds, defined :59-75) vs the network call at :166`  
**Effort:** ~20 min

consumeDeletedIds() unconditionally `removeObject`s stride_deleted_habit_ids, stride_deleted_entry_ids and stride_deleted_group_ids — plus the widget's shared app-group key at :172 — sixty-three lines before the suspension point at :166 `try await api.pushChanges(payload)`. If that call throws (offline, timeout, 401, 5xx, task cancellation, or the 413 above) sync() catches at :94, sets syncError and returns. The ids are gone permanently and nothing re-derives them: the SwiftData objects were already deleted, so the list cannot be reconstructed. Concretely: the user deletes "Meditate" in Settings (SettingsView.swift:481-485 records the habit tombstone plus one per record), taps Sync Now on a train, the push fails. Every later payload has deletedHabitIds: [], so the server keeps the habit row and never writes a tombstone; the iPad never learns of the deletion and shows "Meditate" forever, and a reinstall restores it onto the iPhone too. The habit is effectively undeletable on an unreliable network. Note this fires on EVERY failed push, so while the 10 KB bug is live it is not an edge case at all.

**Fix:** Read without clearing, and clear only on success. Rename consumeDeletedIds() to pendingDeletedIds() with the four removeObject calls stripped out, and after `try await api.pushChanges(payload)` returns at :166 call a new clearDeletedIds(_ deleted:) that removes exactly the ids that were sent — filtering rather than wholesale removal, so ids queued by the user during the in-flight push are not silently dropped.

### Widget and Watch toggle delete a count habit's entire logged day, and push a tombstone for it

**Where:** `StrideWidget/Sources/StrideWidget.swift:80-86; StrideWatch/Sources/WatchTodayView.swift:52-62`  
**Effort:** ~1 h for the shared helper (recommended), ~20 min for two inline branches

ToggleHabitIntent.perform() never reads habit.habitKind. If any record exists for today it calls context.delete(existingRecord); otherwise it appends HabitRecord(date: today) with the default value 1. For a count habit, isCompletedOn is `loggedValue >= targetValue` (Shared/Habit.swift:127-128), so "Drink Water" at 6 of 8 glasses renders in the medium widget as an EMPTY circle (StrideWidget.swift:257) — the destructive tap is not just possible, it is invited. One tap destroys all six logged units with no undo, and trackDeletedEntry (:92) writes the id to the shared app-group defaults so the loss propagates to every other device on the next sync. Tapping again creates a fresh record at 1/8, and Habit.completedDayKeys drops the day from streak and rate math entirely. WatchTodayView.toggleCompletion has the identical defect and is worse: :56-59 loops and deletes EVERY matching record for the day. The main app deliberately does not do this — TodayView.swift:379 routes count habits to incrementCount() at :470-472, and only decrementCount deletes, at value <= 1. This became reachable for real users in 1.2.2, since that is the first build that actually ships the widget.

**Fix:** Extract one shared check-in routine in Shared/ (e.g. `HabitCheckIn.toggle(habit:on:context:)`) that branches on habit.habitKind — for .count, increment an existing record's value and call touch(), or create one at 1, and delete only when value <= 1 — and call it from TodayView, StrideWidget's ToggleHabitIntent, WatchTodayView.toggleCompletion and StrideShortcuts' CompleteHabitIntent. That single extraction also fixes the Siri duplicate-record bug below. If you want the minimal change instead, branch on habitKind inline at both sites.

### Per-habit reminders are never cancelled when a habit is deleted or archived — phantom notifications forever

**Where:** `Stride/Sources/Views/SettingsView.swift:487 (delete), :305 and :378 (archive); Stride/Sources/Services/NotificationService.swift:170, :175-188`  
**Effort:** ~30 min

scheduleHabitReminder registers a REPEATING UNCalendarNotificationTrigger under `stride.habit.reminder.<uuid>` (NotificationService.swift:150, 164-168). `grep -rn removeHabitReminder --include="*.swift" .` returns exactly two hits in the whole codebase: the definition at NotificationService.swift:170 and one call at AddHabitView.swift:411, reached only when the user opens the edit sheet and switches that habit's reminder off. The delete path (SettingsView.swift:487 modelContext.delete(habit)) and both archive paths (:305, :378 habit.isArchived = true) mutate the store and never touch UNUserNotificationCenter. Pending repeating triggers persist in the system notification store across relaunches, and rescheduleAllHabitReminders (:175-188) only fetches habits where reminderEnabled && !isArchived and re-adds those — it never enumerates pending requests to prune orphans, so a stale identifier survives forever. The user swipes to delete "Gym" and still gets "💪 Gym — Time to work on your habit!" at 07:00 every morning, for a habit that no longer exists anywhere in the app. There is no row left to open and toggle off, so the only remedies are turning off Stride's notifications entirely or deleting the app. That is a one-star review with a specific, quotable complaint. The orphans also silently consume slots in iOS's 64-pending-request budget.

**Fix:** Add `NotificationService.shared.removeHabitReminder(for: habit.id)` at SettingsView.swift:487, :305 and :378. Then make rescheduleAllHabitReminders self-healing: fetch center.pendingNotificationRequests(), and remove every identifier carrying the `stride.habit.reminder.` prefix whose UUID is not in the live active-habit set. The sweep is what cleans up the orphans already sitting on existing users' devices — without it, the direct calls only stop new ones.

### A charged-but-unverified purchase is silently dropped: no Pro, no error, transaction never finished, re-dropped every launch

**Where:** `Stride/Sources/Services/StoreService.swift:100-108, caller at :314-326, listener at :147-152, checkVerified at :157-164`  
**Effort:** ~20 min

purchase(_:) handles `.success(let verification)` by running it through checkVerified, which returns nil for `.unverified` (:158-159). It then returns false at :108 WITHOUT finishing the transaction and WITHOUT throwing. The caller purchaseProduct (:314-326) only sets errorMessage/showError in its catch; a returned false just sets isPurchasing = false and does nothing else — there is no else branch on `if success { dismiss() }` at :320-321, so no alert, no dismissal, no state change. But `.success(.unverified)` means Apple DID complete and charge the purchase; only local JWS verification failed (clock skew, a signature hiccup). Because the transaction is never finished, StoreKit re-delivers it to Transaction.updates on every launch, where the listener at :147 runs the same checkVerified and drops it again — so it is never finished and never grants Pro, permanently. The user taps the Lifetime card, is charged, watches "Processing…" disappear with the paywall unchanged, gets no explanation, and can never get the feature. This is precisely the class of failure Sentry would have surfaced and did not.

**Fix:** Switch on the VerificationResult explicitly rather than routing it through the nil-returning helper: on `.unverified(_, let verificationError)` log verificationError and throw a user-facing StoreError so the existing alert at :297-301 fires with a real message. Do the same in listenForTransactions instead of silently dropping. Never return a bare false for a state that means money was taken.

### pullRemote compares UUIDs as case-sensitive raw strings — breaks the App Review demo account and can hard-crash at launch

**Where:** `Stride/Sources/Services/SyncService.swift:172, 243, 250, 253, 257, 282, 316`  
**Effort:** ~45 min including the regression test

Swift's UUID.uuidString always renders UPPERCASE hex; Node's crypto.randomUUID() renders lowercase (server/seed-demo.js:62 and :97, server/routes/habits.js:74 and :202). Two raw-string comparisons break. (a) Line 257 `guard let habit = updatedMap[remoteEntry.habitId] else { continue }` — updatedMap (:250) is keyed by uuidString (uppercase), remoteEntry.habitId is the server string (lowercase), so the lookup misses and EVERY pulled entry is silently skipped; line 282 then deletes every local HabitRecord on a full pull, because remoteEntryIds (:253, lowercase) contains none of the local uppercase ids. The habit upsert itself survives because :193 parses through UUID(uuidString:), which is case-insensitive — which is exactly why habits appear but their history does not. (b) The map miss at :195 sends a lowercase habit into the insert branch at :216, where `habit.id = uuid` produces a UUID byte-identical to one already inserted; habitMap is a snapshot never updated inside the loop, so both rows insert, and the very next statement at :250 traps.

Honest scoping, because it changes how you should weigh this: I grepped Stride/Sources and StrideMac and the app never calls the REST /v1/habits routes. So lowercase ids reach a device only via seed-demo.js — i.e. the App Review demo account (demo@stride-review.com, RELEASE-1.2.1.md:87). This is not a paying-user data-loss event; it is a rejection risk. The reviewer logs in, sees six habits with 0-day streaks, 0% completion and blank calendars, and on a second sync can crash the app. Fix it anyway: it is the same one-line normalization, and it is the thing most likely to sink 1.2.3.

**Fix:** Normalize both sides before comparing. Key every map and set through UUID(uuidString:) (or .lowercased()) rather than raw uuidString, at :172, :243, :250, :253, :282, :293 and :316. Add a SyncReconcileTests case that feeds `UUID().uuidString.lowercased()` as the server id — the existing simulated ids at StrideTests/SyncReconcileTests.swift:88, 138-139 and 167-168 are all produced by UUID().uuidString (uppercase), which is why this stayed green. Then log into the demo account on a device before submitting and confirm streaks and history render.

### Dictionary(uniqueKeysWithValues:) on habit ids traps at runtime on any duplicate

**Where:** `Stride/Sources/Services/SyncService.swift:172 and :250`  
**Effort:** ~5 min

Both lines build habit lookup dictionaries with Dictionary(uniqueKeysWithValues:), which traps with `Fatal error: Duplicate values for key` if two local Habit objects ever share an id. Habit.id has no @Attribute(.unique) in Shared/Habit.swift, so nothing structurally prevents that. The finding above is one route in; any future path that inserts a habit whose UUID already exists produces the same trap. The crash lands inside pullRemote during the launch sync started by StrideApp.swift:37-47 — so it is a hard crash on every launch with no way to recover from inside the app, and with Sentry inert in 1.2.0/1.2.1 it would have been completely invisible. The group reconciliation immediately below at :293 was already hardened with `Dictionary(_, uniquingKeysWith:)`; the habit and entry paths simply were not.

**Fix:** Two lines: `Dictionary(existingHabits.map { ($0.id.uuidString, $0) }, uniquingKeysWith: { a, _ in a })` at :172 and the same shape at :250, matching what :293 already does. Do this even after fixing the id-case bug — it is the crash backstop, and it is five minutes.

### Siri "Complete a Habit" creates a duplicate same-day record for count habits

**Where:** `Stride/Sources/Intents/StrideShortcuts.swift:43-48`  
**Effort:** ~20 min (free if you extract the shared helper)

CompleteHabitIntent.perform() guards only on `habit.isCompletedOn(today)` at :43 and then unconditionally does `habit.records.append(HabitRecord(date: today))` at :47-48. It never checks whether a record for today already exists. For binary habits the two are equivalent (isCompletedOn is `record(on:) != nil`, Shared/Habit.swift:124-125), but for count habits isCompletedOn is `loggedValue >= targetValue`, so any partially-completed count habit falls straight through the guard and gains a SECOND HabitRecord with the same UTC day-key. Everything downstream assumes at most one record per habit-day: Habit.record(on:) at :103-105 returns records.first, and loggedValue, progress and isCompletedOn all read only that one. So "Drink Water" at 5 of 8, after "Hey Siri, complete Drink Water in Stride", replies "Completed 💧 Drink Water!" and the app then shows either 5/8 or 1/8 depending on which duplicate first returns. completionsPerWeekday() double-counts the day, and both records push to the server as independent entries. Repeating the phrase adds another orphan every time.

**Fix:** Replace the guard with an explicit `habit.record(on: today)` lookup: if a record exists, for .binary return "already completed", for .count increment its value toward targetValue and report progress in the spoken result; create a record only when none exists for the day. This is the same shared helper as the widget/watch fix — do them together.

### StatsView keeps a strong reference to a deleted Habit and reads it on the next render

**Where:** `Stride/Sources/Views/StatsView.swift:9, :43, :55, :93-97`  
**Effort:** ~15 min

`@State private var selectedHabit: Habit?` retains a SwiftData @Model object outside the @Query result set, and nothing ever clears it when that habit is deleted. It is auto-populated on first appearance (`.onAppear { if selectedHabit == nil { selectedHabit = habits.first } }`, :93-97), so it is non-nil for essentially anyone who has opened the Stats tab — no tap required. When that habit is deleted (SettingsView.swift:487 modelContext.delete(habit) then save(), or SyncService's remote-tombstone deletions at :178-182 and :242-246, which need no user action at all), the change to the @Query that StatsView also observes marks it dirty; the next body evaluation reads the dead object at :43 (`selectedHabit?.id == habit.id`, once per remaining chip) and at :55, where it is handed to HabitDetailStatsCard / WeeklyBarChart / HeatmapView, which read emoji, name, records and currentStreak(). Property access on an invalidated SwiftData model traps ("This model instance was invalidated because its backing data could no longer be found the store"). There is no isDeleted guard anywhere in the Swift sources. On iPhone the three screens live in a TabView (ContentView.swift:71-95) so the @State survives the tab switch and the stale reference is still there on return. Repro needs two or more habits — with one, the habits.isEmpty branch at :20 short-circuits. Being straight with you: I could not run this on a device, so whether the exact symptom is a trap or a garbage render is unconfirmed. The stale reference itself is certain, the fix is three lines, and with no telemetry this is exactly the crash you would never hear about.

**Fix:** Stop holding the model object. Change to `@State private var selectedHabitID: UUID?`, set it at :47, and resolve per render: `let current = habits.first { $0.id == selectedHabitID } ?? habits.first`. Use `current` at :43 and :55, and delete the .onAppear block at :93-97 entirely — the `?? habits.first` fallback already covers first appearance.


## Should fix

### Entitlement check runs last in a serial network chain at launch, and never re-runs on foreground — paying users see Pro locked

**Where:** `Stride/Sources/App/StrideApp.swift:37-47 (launch task), :58-65 (foreground hook)`  
**Effort:** ~15 min

refreshPurchasedProducts() is the LAST of four sequential awaits: setupNotifications() -> syncIfLoggedIn() -> loadProducts() -> refreshPurchasedProducts(). syncIfLoggedIn() awaits AuthService.waitForSessionRestore() (busy-waits up to 10 s) and then a push and a pull over URLSession with default timeouts — APIClient sets no timeoutInterval anywhere. loadProducts() then burns up to 2+4+8+16 = 30 s of retry backoff (StoreService.swift:66-91) before the entitlement read finally runs. Yet Transaction.currentEntitlements (:133) is a local, offline-capable read that could answer instantly. For that whole window purchasedProductIDs is empty and store.isPro is false, so a customer who already bought Lifetime sees ProLockedCard instead of Insights and Trend (StatsView.swift:58-62), gets the paywall instead of Weekly Review (:81), sees the crown on New Group (AddHabitView.swift:345-366), and reads "Upgrade to Pro" in Settings (SettingsView.swift:73). The willEnterForeground handler at :58-65 calls updateBadge and syncIfLoggedIn only, and there is no scenePhase handler anywhere in the project — so nothing ever re-checks entitlements after that one chain. On macOS it is worse: ContentView.detailView only instantiates the selected tab, so on the default Today tab StoreService.shared is not constructed at all, meaning the Transaction.updates listener is not even installed until the sync finishes.

**Fix:** Move `await StoreService.shared.refreshPurchasedProducts()` to the FIRST line of the .task, ahead of notifications, sync and product loading, and add it to the willEnterForeground handler alongside syncIfLoggedIn(). Touch StoreService.shared in StrideApp.init() so the Transaction.updates listener is installed before any network work happens.

### bestStreak() ignores the schedule and the week unit, so the two streaks on one card contradict each other

**Where:** `Shared/Habit.swift:240-260; unit label hard-coded at Stride/Sources/Views/StatsView.swift:227`  
**Effort:** ~45 min

bestStreak() counts only calendar-consecutive completed day-keys (`let sortedDates = completedDayKeys().sorted()` at :242, then a strict adjacency walk). Unlike currentStreak it never consults isScheduled(on:), so every rest day for a specificDays habit breaks the run; and it has no timesPerWeek branch, so for a weekly-goal habit it counts days while currentStreak (:159-160) counts weeks. StatsView renders the two side by side and hard-codes "days" at :227 while Current Streak takes its unit from habit.streakUnit at :213. So on one row a user with "Gym — Mon/Wed/Fri" who has not missed a session in six weeks reads: Current Streak 18 days, Best Streak 1 days — because no two of their completed days are ever adjacent. A user with "Yoga — 3x per week" at six perfect weeks reads Current 6 weeks, Best 2 days.

**Fix:** Mirror currentStreak's structure: early-return to a weekly best-streak scan when schedule == .timesPerWeek, and for the day path walk the day-key range skipping unscheduled days rather than requiring literal adjacency. Drive the label at StatsView.swift:227 from habit.streakUnit, exactly as :213 already does.

### The overall "Best Streak" tile actually shows the maximum CURRENT streak

**Where:** `Stride/Sources/Views/StatsView.swift:109-111, rendered at :122`  
**Effort:** ~5 min

`private var bestStreak: Int { habits.map { $0.currentStreak() }.max() ?? 0 }` is rendered under the label "Best Streak". It never calls Habit.bestStreak(), which exists at Shared/Habit.swift:240 and is used only by the detail card. So the number collapses the instant a streak breaks: a user whose 200-day meditation streak ended yesterday opens Stats and the tile reads 0 (or 1 once they check in today) — the app looks like it erased their record. And because currentStreak() returns weeks for timesPerWeek habits and days for the rest (Habit.swift:159-160), the max is taken over mixed units and displayed with no unit at all.

**Fix:** `habits.map { $0.bestStreak() }.max() ?? 0` once bestStreak is fixed above — or, if you prefer the smaller change, relabel the tile "Current Streak" and show the unit. Ship it in the same commit as the bestStreak fix.

### 30-day completion rate treats a "X times per week" habit as if it were due all seven days

**Where:** `Shared/Habit.swift:147-149 and :283`  
**Effort:** ~1 h

isScheduled(on:) returns true for every day when schedule == .timesPerWeek, and completionRate(from:to:) builds its denominator from exactly that (`if isScheduled(on: day) { expectedDays += 1 }` at :283). A habit whose goal is N of 7 days is therefore scored against 7 expected days a week and can never exceed N/7. That caps the two most prominent numbers in the app: the per-habit "30-Day Rate" (StatsView.swift:236) and the "30d Avg" tile (:113-115, rendered :124), plus every bar of the Pro 8-week trend. A user who sets "Run — 3x per week" and hits exactly 3 runs every week for a month, never missing, sees "30-Day Rate 43%" sitting next to a healthy multi-week Current Streak, and concludes the flexible-frequency feature is broken or that they are failing. The streak code already knows the correct denominator — currentWeeklyStreak compares weeklyCompletions against timesPerWeek — the rate math just does not use it.

**Fix:** Add a timesPerWeek branch to completionRate(from:to:): sum min(weeklyCompletions(weekStarting:), timesPerWeek) over the whole weeks in the range and divide by timesPerWeek x weeks, pro-rating the partial first and last week, instead of counting individual days.

### The Pro 8-week trend divides the current week by seven days that have not happened yet

**Where:** `Stride/Sources/Views/StatsView.swift:320-322`  
**Effort:** ~10 min

Every bar is completionRate(from: start, to: end) where end is always start + 6 days — including the in-progress week, whose end is in the future. completionRate(from:to:) loops `while day <= endKey` counting every scheduled day into expectedDays with no clamp to today (Habit.swift:280-286), so the not-yet-arrived days of the current week are scored as misses. A Pro subscriber with a daily habit completed every day for months opens Stats on a Monday evening and sees 100, 100, 100, 100, 100, 100, 100, 14 — the last bar a near-empty stub. Tuesday it reads 28, Wednesday 42. The headline chart of a paid feature appears to collapse every single week and only recovers on Sunday. InsightsCard, two views down the same screen, gets this right: its momentum calculation passes `to: todayKey` (:382), so the same week is measured two different ways on one screen. Unlike the day-key bug you fixed in 1.2.2, this affects every timezone including UTC+.

**Fix:** Clamp the current week's end: `let end = min(utc.date(byAdding: .day, value: 6, to: start)!, todayKey)`, matching what InsightsCard already does at :382.

### Weekly Review's rate ignores both the schedule and count-habit targets, so it praises the failing habit

**Where:** `Stride/Sources/Views/WeeklyReviewView.swift:26-37, consumed at :144 ("Best") and :154 ("Needs work")`  
**Effort:** ~15 min

completionRate(for:in:) divides a raw count of habit.records in the date range by the number of elapsed calendar days (`return days > 0 ? Double(completions) / Double(days) : 0`). It never calls isScheduled(on:), so rest days for a specificDays habit and non-goal days for a timesPerWeek habit count as expected days; and it never tests value >= targetValue, so for a count habit any record at all — one glass of an eight-glass goal — counts as a full completion. Habit.completionRate(from:to:) handles both correctly (completedDayKeys() applies the target test at :134-142, and :283 gates the denominator on isScheduled), so this Pro screen contradicts the Stats tab for the same habit and the same week. Concretely, on a Sunday: "Gym — Mon/Wed/Fri", completed on all three scheduled days, shows 43% (3/7) and gets tagged "Needs work"; "Water — 8 glasses/day", where the user logged exactly one glass a day and never came close, shows 100% and is crowned "Best". The paid weekly summary rewards the failed habit and scolds the perfect one.

**Fix:** Delete the local helper and delegate to the model: `habit.completionRate(from: range.start, to: range.end)`, which already handles rest days and count targets.

### Widget timeline is never reloaded for habit add, delete, edit, or after a sync pull — stale for up to 24 hours

**Where:** `Stride/Sources/App/StrideApp.swift:48-53; Stride/Sources/Intents/StrideShortcuts.swift:51`  
**Effort:** ~30 min

WidgetCenter.shared.reloadAllTimelines() is called from exactly three places in the app — TodayView.swift:453 (binary toggle), :519 (count save), and StrideApp.swift:52 via the .habitDataChanged notification, which is posted from exactly one place, StrideShortcuts.swift:51 (grep for habitDataChanged returns only the declaration at :106, the observer at :49 and that single post). ### Entry upsert has no last-write-wins guard, so a stale device silently reverts newer check-in values and notes

**Where:** `server/routes/sync.js:68-75 (the upsert) and :176 (the binding); SyncEntry at Stride/Sources/Services/APIClient.swift:206-213`  
**Effort:** ~45 min, split server/client

upsertHabit (sync.js:64-65) and upsertGroup (:85-86) both refuse stale writes with `AND excluded.updated_at >= <table>.updated_at`. The entry upsert's `ON CONFLICT(habit_id, date) DO UPDATE SET note = excluded.note, value = excluded.value, updated_at = excluded.updated_at` has no WHERE clause at all. It cannot have one today: SyncEntry carries no updatedAt field, and :176 passes the server's own `now` as updated_at, so the stored timestamp carries no information about when the client actually edited the entry. Since every device pushes its full entry set on every sync (SyncService.swift:132-143), the last device to sync wins for every entry it holds, regardless of which edit is newer. Binary habits never notice; quantitative habits and entry notes lose data. Concretely: the iPad records "Water" = 2 in the morning and goes into a bag; during the day the iPhone logs up to 8 and syncs; that evening the iPad comes online, pushes its stale 2, and unconditionally overwrites the 8 — then the next pull propagates 2 back to the iPhone. The day's progress is destroyed with no error and no recovery.

**Fix:** Add updatedAt to SyncEntry and set it whenever value or note changes — HabitRecord.updatedAt and touch() already exist at Shared/Habit.swift:309-325. On the server, bind `field(e, "updatedAt") || now` at :176 and add `WHERE excluded.updated_at >= habit_entries.updated_at` to the conflict clause. The server half is forward-compatible (old clients fall back to now and keep today's behaviour), so it can ship with the body-limit hotfix ahead of the client build.

### The `since` cursor uses the device clock and ignores the server's own serverTime, leaving a hole in the change feed

**Where:** `Stride/Sources/Services/SyncService.swift:90-92; the decoded-but-unused field at Stride/Sources/Services/APIClient.swift:232`  
**Effort:** ~20 min

After a successful sync the client stores `Self.iso8601.string(from: Date())` — the device's local clock — and sends it back as ?since= on the next pull. The server compares it against its own clock: habits.updated_at > ?, habit_entries.updated_at > ?, habit_groups.updated_at > ? and deletion_tombstones.deleted_at > ?, all written with the server's new Date().toISOString(). The pull response already returns an authoritative serverTime (sync.js:298) and SyncPullResponse decodes it (APIClient.swift:232) — grep confirms it is never read anywhere. Two consequences. (a) A device whose clock runs a few minutes fast stores a cursor in the server's future; anything another device writes in that window is skipped from EVERY subsequent incremental pull, because those rows are never touched again — the devices diverge silently with no error, and tombstones recorded in that window never arrive. (b) There is no overlap window at all, so anything committed between the server's SELECT and the client capturing Date() is skipped even with perfect clocks. (b) is the one that matters — it does not depend on clock skew and it is a genuine race on every sync.

**Fix:** Persist response.serverTime as the next cursor instead of the local Date(), minus a small safety overlap (60 s) so rows written during the pull are not missed. This needs pullRemote to hand the value back up to sync() rather than setting it there.

## Deliberately not doing

- **Old 1.1 clients wipe v2 habit fields on every push** — Real and verified, not speculative: 1.1's SyncHabit (git dbdab48:Stride/Sources/Services/APIClient.swift:169-181) has no note, kind, targetValue, unit, scheduleKind, timesPerWeek, activeDaysMask or groupId, and its pushLocal sends `updatedAt: Self.iso8601.string(from: Date())` for every habit on every push. So the conflict guard `excluded.updated_at >= habits.updated_at` (sync.js:65) always passes for a 1.1 push, and the DO UPDATE writes sync.js:180-187's defaults — kind 'binary', target_value 1, unit NULL, schedule_kind 'daily', times_per_week 7, active_days_mask 127, group_id NULL, note NULL — over whatever 1.2 stored. Merely opening the old app on a second device destroys the newer device's habit configuration, and 1.2's next pull applies it unconditionally at SyncService.swift:205-211. But: it only bites a user running 1.1 on one device and 1.2.x on another, that population predates 2026-06-07 and shrinks every week, and the fix is genuinely fiddly. COALESCE cannot help, because NULL is a LEGITIMATE value for note, unit and groupId — the server cannot distinguish "the client omitted this key" from "the user cleared this field" without building the UPDATE SET list dynamically from the keys actually present in each request body. That is a meaningful rewrite of the hottest server code path, in the same release where you are already changing that file twice, to protect a shrinking cohort. Skip it for 1.2.3. If you want visibility for near-zero cost, log a warning in the push handler when a habit object arrives with no `kind` key — that tells you whether any 1.1 client is still pushing at all, and you can decide with data later.
- **Rewriting pushLocal to be incremental** — This is the right long-term design and it is the root cause behind two separate findings — sending the entire dataset on every sync is what makes the 10 KB ceiling possible, and it is what makes the stale-entry overwrite reachable at all (a device that only sent what it changed could not push a three-day-old value back over a newer one). But it is by far the largest change on this list, it touches the reconciliation logic that 1.2.2 only just stabilised, and it needs its own test pass covering first-upload chunking and the changed-since filter. Meanwhile raising the sync body limit to 5 MB buys years of headroom: a user with 1,000 check-ins serialises to about 180 KB, and I confirmed a 206 KB push parses fine under that limit. Do not put this in a bug-fix release. Do it when you next open sync deliberately, with tests, as its own piece of work.
